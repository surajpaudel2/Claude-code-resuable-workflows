Section 13: Background jobs done, written in backend.md section 13

Decisions applied: ShedLock from the start (PostgreSQL table), fixedDelay by default (cron only for calendar times), next run is the retry (@Retryable only around vendor calls, max 3, backoff), batch size 100 set in yml.

Folders (new items only)

shared/
└── config/SchedulingConfig.java                 @EnableScheduling, @EnableSchedulerLock, @EnableRetry, job thread pool, LockProvider

<module>/
├── job/
│   ├── ExpiredOrderCleanupJob.java              thin trigger: lock, call service, log
│   └── OrdersJobProperties.java                 @ConfigurationProperties record: batch size, delays
└── service/OrderService.java                    expireOverdue(batchSize): one batch, one transaction

src/main/resources/db/migration/shared/
└── V202611161100__shared_create_shedlock.sql    the lock table

Flow of one run

Scheduler thread (pool "job-")  → sets a new correlationId in MDC
 → @SchedulerLock                → only one instance gets the lock, others skip silently
 → ExpiredOrderCleanupJob.run()  → logs started
 → loop: orderService.expireBatch(batchSize)    each call = one short transaction, returns rows processed
 → stop when a batch returns less than batchSize (or max batches reached)
 → logs completed (processed_count, duration_ms)
 → on unexpected failure: logs failed once with stack trace (the job is its own failure boundary)
 → next fixedDelay run picks up whatever is left (that is the retry)

The job

// orders/job/ExpiredOrderCleanupJob.java
@Slf4j
@Component
@RequiredArgsConstructor
public class ExpiredOrderCleanupJob {

    private static final String JOB_ID = "orders.expired-cleanup";
    private static final int MAX_BATCHES = 100;                       // safety stop

    private final OrderService orderService;
    private final OrdersJobProperties properties;

    @Scheduled(fixedDelayString = "${app.orders.jobs.expired-cleanup.fixed-delay}")
    @SchedulerLock(name = JOB_ID,
            lockAtMostFor  = "${app.orders.jobs.expired-cleanup.lock-at-most-for}",
            lockAtLeastFor = "${app.orders.jobs.expired-cleanup.lock-at-least-for}")
    public void run() {
        long start = System.nanoTime();
        int total = 0;
        try {
            int batchSize = properties.expiredCleanup().batchSize();
            for (int i = 0; i < MAX_BATCHES; i++) {
                int processed = orderService.expireBatch(batchSize);  // own transaction per call
                total += processed;
                if (processed < batchSize) break;
            }
            log.atInfo()
               .addKeyValue("event", "order.expired-cleanup.completed")
               .addKeyValue("job_id", JOB_ID)
               .addKeyValue("processed_count", total)
               .addKeyValue("duration_ms", Duration.ofNanos(System.nanoTime() - start).toMillis())
               .log("Expired order cleanup finished");
        } catch (Exception e) {
            log.atError().setCause(e)
               .addKeyValue("event", "order.expired-cleanup.failed")
               .addKeyValue("job_id", JOB_ID)
               .addKeyValue("attempt", 1)
               .log("Expired order cleanup failed");                  // next run retries
        }
    }
}

// orders/service/OrderService.java: the job's only call, safe to run twice
@Transactional
public int expireBatch(int batchSize) {
    List<OrderEntity> overdue = orderRepository.findOverdueNotExpired(Instant.now(), PageRequest.of(0, batchSize));
    overdue.forEach(OrderEntity::markExpired);                        // rows already expired are not selected again
    return overdue.size();
}

Rules (will go into backend.md)

Place        jobs live in <module>/job/, named <What>Job. A job is a thin trigger: lock, one call to a service, log. No business logic.
Schedule     never hardcoded. Values come from application.yml under app.<module>.jobs.<name>.
             fixedDelay by default. Cron only for calendar times ("every day at 02:00"), in UTC.
Pool         shared/config/SchedulingConfig provides a dedicated pool, so jobs never block listeners. Each run gets a new correlationId.
Locking      every job has @SchedulerLock (ShedLock, table "shedlock" in PostgreSQL, Flyway migration in shared).
             Name = job id. lockAtMostFor is longer than the longest normal run.
Idempotent   every job is safe to run twice. It selects only rows that still need work.
Batches      bounded batch size from yml, one short transaction per batch inside the service, a max-batches safety stop.
             The job loop never sits inside one transaction.
Retries      the next run is the retry. @Retryable (max 3, exponential backoff) only around vendor calls and only for transient errors.
Failure      the job is its own failure boundary: one terminal log with stack trace. One bad item never stops the batch.
Logging      events <module>.<job>.started|completed|failed, fields job_id, attempt, processed_count, duration_ms.
             Summaries only, never one line per item. An idle run logs at DEBUG.
Settings     typed @ConfigurationProperties record with @Validated, kebab-case keys.
Tests        the service method (including a second run that does nothing). Lock behavior later with Testcontainers.
